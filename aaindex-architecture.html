1. Application Overview

The AAIndex Frontend is a browser-based bioinformatics tool for exploring, analysing, and visualising the AAIndex database — a curated collection of amino acid physicochemical property indices published by Kawashima & Kanehisa (Nucleic Acids Research). The database encodes quantitative properties (hydrophobicity, charge, volume, flexibility, etc.) for each of the 20 standard amino acids, and has been widely used in structural biology, protein engineering, and machine-learning feature pipelines.

The application spans all three AAIndex sub-databases:

  • AAIndex1 — 566 scalar-value indices (one number per amino acid)
  • AAIndex2 — Substitution/mutation matrices (20×20 values)
  • AAIndex3 — Contact-potential matrices (20×20 values)

Combined this gives 707+ records browsable, searchable, and analytically explorable entirely in the browser with no backend server required.

Design principle: The application deliberately has no backend. All data is bundled at build time as JSON. All computation runs client-side. This eliminates operational complexity, reduces cost to zero, and makes the app instantaneously available anywhere — including offline (after initial load).

4. Data Layer

Data Strategy: Static JSON at Build Time

Rather than fetching data from an API at runtime, all three AAIndex databases are converted to JSON and placed in src/data/. Vite bundles these files as ES module imports, making them available synchronously from the moment the JS chunk loads — zero network latency for data access.

This is viable because the data is:

  • Static — AAIndex is a curated, versioned database that rarely changes
  • Bounded in size — ~1.5 MB for AAIndex1 (largest), compresses to ~300 KB gzip
  • Read-only — users browse and analyse but never write back

5. Routing & Page Inventory

Routing is handled by React Router v6 using BrowserRouter in SPA mode. A vercel.json rewrite rule catches all paths and serves index.html, allowing React Router to handle navigation client-side without 404s on direct URL access or refresh. 

// vercel.json
{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }

All routes are wrapped in a shared Layout component (Navbar + content outlet):

/explorer
Record Explorer
Browse all 707 records across all three databases. Full-text fuzzy search via Fuse.js, category filter dropdown, favourites filter toggle, and per-category statistics panel (mean, min, max, std dev per amino acid).
/records/:accession
Record Detail
Deep-dive view. Bar chart of amino acid values, z-score normalisation toggle, correlation coefficient table, similar records panel, live PubMed abstract fetch, citation helper, embeddable iframe snippet, CSV / JSON export, and add-to-compare action.
/sequence
Sequence Analysis
Three-tab tool: (1) Sequence Encoder — maps protein sequence to property values as a line chart; (2) Sliding Window — smoothed Kyte-Doolittle-style profile with adjustable window size; (3) Multi-property Heatmap — simultaneous encoding by multiple indices side-by-side.
/correlations
Correlation Explorer
Three-tab tool: (1) Force-directed Network — SVG graph of indices linked by Pearson r above a threshold; (2) Scatter Plot — any two indices plotted head-to-head per amino acid; (3) Redundancy Filter — list all indices correlated above threshold with a chosen target.
/compare
Comparator
Side-by-side comparison of up to 4 records simultaneously. Grouped bar chart, z-score normalise toggle for cross-scale comparison, and a collapsible drawer for managing the comparison selection.
/visualise
Visualiser
Flexible visualisation picker for AAIndex1 records: bar chart, radar chart, or matrix heatmap. Useful for custom presentation or data exploration.

6. State Management

Zustand Store

Global state is managed by a single Zustand store defined in src/store/useAAIndexStore.ts. Zustand was chosen over Redux/Context API because:

  • No boilerplate (no reducers, no action creators, no Provider wrapping)
  • State and actions co-located in one place
  • Minimal re-render overhead — components subscribe to only the slice they need
  • Tiny bundle footprint (~1 KB)

localStorage Persistence

Favourites are the only state persisted across sessions, written to localStorage under the key aaindex_favourites. The load/save logic is minimal and contained within the store file itself — no persistence middleware is needed. 

const FAVS_KEY = 'aaindex_favourites'
const loadFavs = (): string[] => {
  try { return JSON.parse(localStorage.getItem(FAVS_KEY) ?? '[]') } catch { return [] }
}
const saveFavs = (favs: string[]) => localStorage.setItem(FAVS_KEY, JSON.stringify(favs))

7. Core Utilities & Algorithms

All computation lives in src/lib/ as pure, framework-free TypeScript functions.

seqUtils.ts — Sequence Encoding

encodeSequence(seq, values)

Maps a protein sequence (IUPAC single-letter codes) to an array of { pos, aa, value | null } tuples using a provided AAIndex1 value map. Returns null for any position that is not a standard amino acid or not covered by the chosen index — preserving missingness rather than imputing.

slidingWindowEncode(encoded, windowSize)

Applies a symmetric sliding-window average over an encoded sequence — the algorithm used in the classic Kyte-Doolittle hydrophobicity profile (1982). Edge positions use truncated windows (averages the available residues rather than padding with zeros). This faithfully replicates the original Kyte-Doolittle behaviour.

pearsonR(xs, ys)

Computes the Pearson product-moment correlation coefficient for two numeric arrays. Used in the Correlation Explorer to quantify linear relationships between AAIndex1 properties. Handles the degenerate case (zero variance) by returning 0 rather than NaN. 

r = Σ((xᵢ - x̄)(yᵢ - ȳ)) / ( √Σ(xᵢ - x̄)² × √Σ(yᵢ - ȳ)² )

zScoreNormalise(values)

Normalises a Record<string, number> of amino acid values to z-scores: subtracts mean and divides by standard deviation. When comparing indices with different numeric ranges (e.g. volume vs. flexibility), z-score normalisation puts them on a common scale. Standard deviation is floored at 1 to avoid division by zero for constant indices.

exportEncodingAsCSV(accession, seq, encoded)

Serialises an encoded sequence to a three-column CSV (position, amino_acid, value) and triggers a browser download using file-saver.

statsUtils.ts — Category Statistics

categoryStats(db, category)

For a given category (or all categories if empty), aggregates per-amino-acid statistics (mean, min, max, standard deviation, count) across all matching AAIndex1 records. Displayed in the Explorer as a summary bar chart when a category filter is active.

search.ts — Fuzzy Search Index

Wraps Fuse.js with a standard configuration: searches across accession, description, and category fields with a threshold of 0.35 (roughly "starts-with or very close match"). The index is built once per database and reused.

exportUtils.ts — Data Export

FunctionOutput
exportValuesAsCSV(acc, values)Two-column CSV: amino acid code + value
exportRecordAsJSON(acc, record)Full record object as formatted JSON
exportMatrixAsCSV(acc, matrix)20×20 substitution matrix as CSV with row/column headers

aminoAcids.ts — Constants

Provides canonical amino acid ordering arrays (AA_ORDER_ALPHA), full English names for tooltip display (AA_FULL_NAMES), and the set of 20 standard residue codes (VALID_AAS).

Custom SVG: Force-Directed Network (Correlation Network tab)

The correlation network is custom SVG rendered by React, not Recharts. It implements a simplified force-directed layout algorithm from scratch:

  • Repulsion — Coulomb-like inverse-square force pushing all node pairs apart
  • Attraction — Spring force pulling connected nodes together (proportional to distance)
  • Gravity — Weak centripetal force toward canvas centre to prevent drift
  • Damping — Velocity multiplied by 0.82 each tick to dissipate energy and converge
  • Bounding — Node positions clamped to canvas bounds (24px margin)

Simulation runs in requestAnimationFrame ticks for up to 300 iterations or until max velocity drops below 0.3. The final stable positions are committed to React state and the SVG re-renders once — preventing continuous repaints post-convergence. 

// Repulsion (Coulomb-style)
const f = rep / (dx² + dy²)
node.vx += (dx / |d|) * f

// Attraction (spring)
const f = att * distance
source.vx += (dx / d) * f; target.vx -= (dx / d) * f

// Damping per tick
node.vx *= 0.82

Node size is proportional to degree (number of edges above threshold). Edge colour encodes sign: indigo for positive r, red for negative r. Edge opacity scales with correlation strength. Clicking a node navigates to that record's detail page.

Custom Canvas: Matrix Heatmap

The 20×20 substitution matrix is rendered as a CSS-grid colour table in MatrixHeatmap.tsx, with cell background colour linearly interpolated between blue (low) and red (high) through white at the midpoint.

Multi-property Heatmap (Sequence Analysis)

Renders as a raw HTML div grid where each cell's background-color is set inline via the same blue-white-red lerp function. Cell width is dynamically computed to fit the sequence length within a 700 px container. Missing values (amino acids not covered by an index) are rendered with a CSS diagonal-stripe pattern to distinguish "no data" from a zero or near-zero value.

9. Search

The Explorer uses Fuse.js to build an in-memory fuzzy-search index over all records in the active database. The index covers three fields:

FieldExample value
accession"KYTJ820101"
description"Hydrophobicity index (Kyte-Doolittle, 1982)"
category"hydrophobic"

Configuration: threshold: 0.35 (tight enough to avoid irrelevant results), includeScore: true (results sorted by relevance). The index is rebuilt only when the active database changes.

Search, category filter, and favourites filter are applied in combination. The result pipeline is: fuzzy search → category filter → favourites filter → rendered cards.

10. External API Integration

NCBI E-utilities: PubMed Abstract Fetch

The only external API call in the application is an optional fetch to the NCBI E-utilities API to retrieve a publication abstract for records that have a PubMed ID (pmid field).

User clicks "Load abstract"
→
NCBI efetch API
→
Module-level cache Map
→
Rendered in <pre>

The fetch is lazy (only fires when the user clicks "Load abstract") and cached in a module-level Map<string, string> for the lifetime of the page session. Repeated visits to the same record do not re-fetch. 

const url = `https://eutils.ncbi.nlm.nih.gov/entrez/eutils/efetch.fcgi
  ?db=pubmed&id=${pmid}&rettype=abstract&retmode=text`
CORS note: NCBI's E-utilities serve responses with permissive CORS headers, so this fetch works directly from the browser without a proxy.

Error Handling

The PubMedAbstract component renders three distinct states: loading (animated pulse), error (red message with HTTP status), and success (scrollable pre-formatted text). The fetch is not retried automatically.

Deployment: Vercel

The project is deployed to Vercel as a static site. The build command is tsc -b && vite build — TypeScript compilation (type check only, Vite transpiles the actual code) followed by Vite's Rollup-based production build.

Key Vercel configuration (vercel.json):

{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }

This single rewrite rule makes all paths serve index.html, enabling React Router's BrowserRouter to handle navigation. Without it, direct navigation to /records/KYTJ820101 would 404.

CI/CD

Vercel's GitHub integration provides automatic preview deployments on every push/PR and production deployment on merge to main. No custom CI pipeline is configured — Vercel's build infrastructure handles it.

12. Key Technical Decisions

Decision 1: No Backend / Static Data

Chosen: Bundle all data as JSON, served as static files.
Alternative: REST API or GraphQL backend serving records from a database.
Rationale: The data is small (~1.5 MB compressed), read-only, and changes infrequently. A backend would add hosting cost, ops burden, and latency with zero benefit. Static delivery is also faster — data arrives with the JS bundle rather than in a separate network round-trip.

Decision 2: Zustand over Context API or Redux

Chosen: Zustand.
Rationale: Context API re-renders all consumers when any value changes — harmful when global state (e.g. activeDB) triggers re-renders on pages that don't use it. Redux is correct but verbose for this scale. Zustand provides fine-grained subscriptions in 3 KB.

Decision 3: Recharts over D3 or Chart.js

Chosen: Recharts (with custom SVG for the network graph).
Rationale: Recharts integrates naturally with React's rendering model — charts are declared as JSX and update reactively. D3 manipulates the DOM imperatively, which conflicts with React's virtual DOM. Chart.js renders to Canvas, making it harder to style consistently with Tailwind. For the force-directed network (which requires custom simulation logic), plain SVG is the right tool.

Decision 4: Fuse.js for Search

Chosen: Fuse.js in-memory fuzzy search.
Rationale: The record set is bounded (~700 items) and entirely loaded into memory. A server-side search endpoint is unnecessary. Fuse.js handles typos and partial matches (e.g. "kyte" finding "Kyte-Doolittle") which a plain includes() check would miss.

Decision 5: TypeScript Strict Mode

Chosen: Full TypeScript coverage with typed interfaces for all DB shapes.
Rationale: JSON data is cast to typed interfaces at import time. This ensures any component accessing record fields is checked at compile time, preventing the most common class of runtime errors (accessing undefined fields on malformed data).

Decision 6: Lazy PubMed Fetch (Click-to-Load)

Chosen: Fetch only when the user clicks "Load abstract".
Rationale: Auto-fetching on page load would fire 707 potential external requests as users browse records. NCBI rate-limits the E-utilities API at 3 req/s without an API key. The lazy pattern respects the API and only fetches when the user explicitly wants the abstract.

Decision 7: Custom Force-Directed Layout (No D3-Force)

Chosen: Bespoke Coulomb + spring simulation in requestAnimationFrame.
Rationale: Adding d3-force (~8 KB gzip) for one visualisation was disproportionate. The custom implementation covers the needed physics (repulsion, attraction, damping, gravity, boundary clamping) in ~60 lines.

14. Limitations & Future Considerations

Current Limitations

LimitationImpact
No backend / no user accounts Favourites and comparison state are per-browser only. Cannot share a saved list across devices or with collaborators.
All data bundled at build time Adding new records or correcting data requires a full rebuild and redeploy. Not suitable if data needs to be updated frequently.
NCBI API rate limit (3 req/s) Rapid navigation between records with PubMed IDs could trigger rate limiting if the user opens many abstracts quickly. No retry or back-off logic is implemented.
Force-directed network scalability The O(n²) repulsion calculation and single-threaded requestAnimationFrame loop struggles above ~150 nodes. Capped at 150 in the UI via a slider.
No offline support No Service Worker / PWA cache. Requires initial network access to load the app.
Mobile layout Responsive breakpoints are present but the two-column sidebar+chart layouts on Sequence Analysis and Correlation Explorer are cramped on small screens.

Potential Future Extensions

  • REST / GraphQL API — if the data set grows or needs user-generated content (custom indices, annotation layers), a backend would be necessary.
  • Web Worker for force simulation — offloading the physics loop to a Worker thread would unblock the UI during network layout, enabling larger graphs.
  • Shareable URLs — encoding the current comparison selection or sequence into the URL query string would enable link sharing.
  • Service Worker / PWA — since all data is bundled, a cache manifest would make the app fully offline-capable after first load.
  • BLAST / alignment integration — accepting a FASTA file and running sequence similarity search would add value for the bioinformatics use case.
  • Export charts as PNG/SVG — html2canvas is already a dev dependency, suggesting this was considered.
